# Kommitly — Data Model

Status: **specification only.** No SQL has been written. Nothing in this
document exists in the database yet.

This describes every model Kommitly needs, its fields, and its types. It is
the input to the first migration, not the migration itself.

---

## Conventions

These apply to every table below and are not repeated in each one.

| Concern | Rule |
| --- | --- |
| Identifiers | `uuid`, generated by the database. The sole exception is `profiles.id`, which **is** the `auth.users.id`. |
| Timestamps | `timestamptz` always. Never a bare `date` + `time` pair — that combination cannot answer "is this in the past?" without guessing a timezone. |
| Money | `bigint`, in **CAD cents**. Never a floating point type: `0.1 + 0.2 != 0.3` is not acceptable in a wallet. The currency code is held in `market_settings` rather than assumed, but every amount column in this model is CAD minor units. |
| On-chain amounts | `bigint` lamports. Only ever appears on deposits and withdrawals. |
| Enumerations | Postgres `enum` types, listed with each table. |
| Audit columns | `created_at` on everything; `updated_at` where rows are edited. |
| Row Level Security | Enabled on every table in the same migration that creates it. |

### Why the ledger is fiat and not SOL

Users deposit SOL; the moment it lands it is converted and credited as fiat.
Every balance, stake, price and payment in this model is therefore fiat cents.

The consequence to be aware of: SOL is a **rail**, not the unit of account. A
user who deposits and later withdraws carries the price movement in between.
The rate used is recorded on the deposit and withdrawal rows so this is always
reconstructable rather than lost.

### Where private keys live

**Nowhere in this database.** Kommitly is custodial, but the signing keys are
held by the wallet Cloud Function's key management, never in a table and never
in a column. The database stores the public address and nothing else. This is
restated in the service contract.

## 1. `profiles`

Extends `auth.users`. One row per account, created on sign-up.

**Email is deliberately absent.** It already exists in `auth.users`, and §2 of
the product spec requires that one marketplace user cannot see another's email.
Mirroring it into a table that other users can read would work directly against
that. Anything needing the email reads `auth.users` server-side.

There is also **no password column** — authentication is passwordless email
OTP, so no password exists anywhere in the system to store.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK, and FK to `auth.users(id)` on delete cascade. |
| `display_name` | `text` | no | Shown to other users. |
| `description` | `text` | yes | Public bio. |
| `reputation` | `numeric` | yes | Written **only** by the reputation Cloud Function. Null means "not yet calculated" — deliberately not defaulted to a number, because an invented starting score would be indistinguishable from a real one. |
| `reputation_updated_at` | `timestamptz` | yes | When the function last wrote the score. |
| `commitments_total` | `integer` | no | Default 0. Every commitment this user has been part of, in either role. |
| `commitments_successful` | `integer` | no | Default 0. Meetup verified and the commitment fulfilled. |
| `commitments_expired` | `integer` | no | Default 0. |
| `commitments_cancelled` | `integer` | no | Default 0. |
| `commitments_ignored` | `integer` | no | Default 0. Seller-side only — only a seller can ignore an incoming request. |
| `commitments_stale` | `integer` | no | Default 0. Commitments that ended with nobody at fault — see below. |
| `email_receipts_enabled` | `boolean` | no | Default false. When on, the user is emailed a receipt. Opt-in, not opt-out. |
| `last_vote` | `timestamptz` | yes | Most recent charity vote. |
| `last_vote_choice` | `uuid` | yes | FK to `charities(id)`. |
| `created_at` | `timestamptz` | no | |
| `updated_at` | `timestamptz` | no | |

### The naming rule

**"Transaction" is wallet vocabulary and appears nowhere on a profile.** A
profile counts *commitments*, because it is commitment behaviour — showing up,
cancelling, ignoring a request — that reputation is built from. Money movement
is a separate concern that lives in `wallet_transactions` and is the only place
the word transaction is used.

This also resolves a duplicate. The original model had `Transactions_to_date`
while §32 had `Transactions_completed`; those were two names for overlapping
ideas. They are now two clearly distinct counters:

- `commitments_total` — how many the user has been involved in at all
- `commitments_successful` — how many actually ended in a verified meetup

Together those answer "how experienced is this person" and "how reliable are
they", which one merged counter could not.

### `commitments_stale`

This replaces the previously undefined `transactions_unverified`. A stale
commitment is one where **neither party is to blame and both were fully
refunded**, because Kommitly lacked the evidence to attribute responsibility.

Two situations produce it:

- neither party checked in
- both parties checked in, but QR #1 was never scanned

In both cases both stakes are returned and no no-show is recorded against
anyone. The count is kept anyway, because a user with a long tail of stale
commitments is a signal worth having even though no single one was their fault
— and §23 is explicit that the event should still be recorded.

**A stale commitment is not a penalty.** Whether it influences reputation at
all is for the reputation function to decide, not this model.

### Buyer and seller behaviour

§8 requires the two roles stay distinguishable. These counters are aggregates
and cannot express that on their own — so rather than doubling every column,
the role-level detail lives in `commitment_events` (§11), which records the
actor and their role for every state change. The reputation Cloud Function
derives any role-specific figure from there, and this table never changes
shape as the reputation algorithm evolves.

## 2. `charities`

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK. |
| `name` | `text` | no | |
| `description` | `text` | yes | |

**A charity holds a wallet, exactly like a user does.** There is no separate
payout mechanism and no address column here: forfeited stakes move into the
charity's own wallet through the same ledger every other transfer uses. See
§15, where `wallets` is owned by either a profile or a charity.

The benefit is that charity money is not a special case. A forfeit is an
ordinary transfer with an ordinary audit trail, and "how much has this charity
received" is answered by the same query that answers it for anyone else.

## 3. `charity_votes`

`profiles.last_vote` and `profiles.last_vote_choice` remain as specified and
hold the most recent vote. This table holds the history, which is what makes a
leaderboard, a trend and an auditable tally possible — those two fields alone
overwrite the previous vote and lose it.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK. |
| `profile_id` | `uuid` | no | FK to `profiles(id)`. |
| `charity_id` | `uuid` | no | FK to `charities(id)`. |
| `voted_at` | `timestamptz` | no | |
| `vote_month` | `date` | no | The first day of the month the vote belongs to, derived from `voted_at`. |

**One vote per user per calendar month**, enforced by a unique constraint on
`(profile_id, vote_month)`.

The month boundary is decided in **`America/Vancouver`**, held as
`market_settings.vote_timezone`. A vote cast at 11pm on the 31st belongs to the
month it was still in locally, not the month UTC had already moved to.

`vote_month` is stored rather than computed inside the constraint, because a
unique index over a timezone-dependent expression is fragile — the month a vote
falls in would shift with the server's configuration. Resolving it once at
write time and storing the result makes the rule explicit and stable.

## 4. `meetup_locations`

Owned by the **seller**, not by a listing. A seller defines their safe meetup
spots once and reuses them.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK. |
| `profile_id` | `uuid` | no | FK to `profiles(id)` — the seller who owns it. |
| `name` | `text` | no | e.g. "Front entrance, Central Library". |
| `latitude` | `double precision` | no | Stored at full precision. |
| `longitude` | `double precision` | no | Stored at full precision. |
| `is_archived` | `boolean` | no | Default false. Archived rather than deleted, so historical commitments keep a valid reference. |
| `created_at` | `timestamptz` | no | |
| `updated_at` | `timestamptz` | no | |

### Precision matters here

A meetup location should be as precise as the seller can make it — a specific
entrance, not a neighbourhood. `double precision` keeps roughly 7 decimal
places, which is about 1cm, so nothing is lost by the column type.

The reason to care: the check-in radius is 200m, and a location recorded
sloppily shifts that whole circle. A pin dropped 150m from where the seller
actually waits means someone standing next to them can fail to check in, while
someone 350m away succeeds. The radius is only as meaningful as the point it
is measured from.

## 5. `listing_meetup_locations`

The per-listing override. This table encodes one rule that must be implemented
exactly, because it is not obvious from the columns:

> **If a listing has no rows here, every one of that seller's non-archived
> locations applies to it. If it has one or more rows, only those apply.**

Absence means "all", not "none". That is what makes the default behaviour —
reuse everything — free, while still allowing a listing to be restricted.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `listing_id` | `uuid` | no | FK to `listings(id)`. Composite PK with the next column. |
| `meetup_location_id` | `uuid` | no | FK to `meetup_locations(id)`. |

## 6. `availability_rules`

Seller-owned **recurring weekly** availability, following the same two-level
pattern as locations.

A seller does not enter dates. They say "Tuesdays, 5pm to 8pm" once, and that
holds every week until they change it.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK. |
| `profile_id` | `uuid` | no | FK to `profiles(id)` — the seller. |
| `day_of_week` | `smallint` | no | 0 = Sunday through 6 = Saturday, matching Postgres `extract(dow from ...)`. |
| `start_time` | `time` | no | Local wall-clock time. |
| `end_time` | `time` | no | Must be after `start_time`. |
| `timezone` | `text` | no | IANA name, e.g. `America/Vancouver`. |
| `is_archived` | `boolean` | no | Default false. Archived rather than deleted so past commitments keep a valid reference. |
| `created_at` | `timestamptz` | no | |

### Why the timezone column is not optional

"Tuesday 5pm" is not an instant. It only becomes one when a timezone resolves
it — and the answer changes twice a year. A seller free 5pm–8pm local is free
at a different UTC hour in July than in January.

Storing wall-clock `time` plus an IANA timezone lets Postgres handle daylight
saving, and preserves what the seller actually meant: "evenings after work",
not "a fixed UTC offset". Storing `timestamptz` here instead would freeze one
offset and silently drift by an hour for half the year — the kind of bug that
shows up as people arriving at the wrong time in March and October.

### Rules generate candidates; commitments store instants

An availability rule is not itself bookable. It describes when a seller is
generally free. The buyer picks a concrete date and time from the candidates a
rule produces, and `commitments.scheduled_at` stores that resolved instant.

This distinction matters for the next part: what gets consumed is a specific
moment, never the weekly rule.

### A commitment consumes its moment

**Once a buyer and seller both hold a commitment at a given time, that moment
is taken.** It must stop being offered to anyone else.

This is a real constraint, not a display preference: a seller cannot be in two
places at once, so two accepted commitments at the same time would guarantee
at least one no-show — and the model would then penalise someone for a
situation the platform created.

The moment is held from the instant the seller **accepts**, not when a buyer
requests. Several buyers may request the same time while it is unaccepted; the
first acceptance takes it, and the others can no longer be accepted for it.

Enforcement is a partial unique index over `(seller_id, scheduled_at)`
restricted to **live** statuses only, so a cancelled or expired commitment
releases the moment again. See "What a commitment is unique on" under §10 for
the companion rule covering the listing itself.

Note that this constrains the seller's calendar, not the rule. A seller with a
Tuesday 5–8pm rule can hold commitments on many different Tuesdays, and several
at different times within one evening — just never two at the same instant,
even for different listings.

### `listing_condition`

`new` · `used_like_new` · `used_good` · `used_fair`

Deliberately the same four grades Facebook Marketplace uses. A seller choosing
a condition and a buyer reading one both arrive with that vocabulary already
learned, and inventing a different scale would only make listings harder to
compare.

### `listing_status`

`draft` · `active` · `reserved` · `sold` · `withdrawn`

`/discover` shows only `active`. `reserved` covers an item with a live accepted
commitment against it, so it stops appearing in search without being marked
sold.

**`reserved` returns to `active` automatically** when its commitment is
cancelled, expires, or goes stale. The seller does not re-list by hand. This
must be automatic: a seller whose buyer cancelled at 2am should not wake up to
an item that silently stopped being visible.

### One listing is one item

**There is no quantity field, deliberately.** A listing represents a single
physical item, and a seller with three identical chairs creates three listings.

That constraint is what makes the rest of the model work. Because an item is
singular, it can carry at most one live commitment, which is what `reserved`
expresses and what lets the platform promise a buyer that the thing they are
driving across town for is actually still available. A quantity column would
break that promise quietly — two buyers could both hold a commitment on "the
last one".

### Check-ins as timestamps, not booleans

The original model lists `Buyer Check-in`, `Seller Check-in` and
`Meetup Confirmed` as flags. They are modelled here as timestamps instead, for
two reasons: the one-hour window in §16 is impossible to evaluate without
knowing *when* the first check-in happened, and a timestamp answers the boolean
question for free (`buyer_checked_in_at IS NOT NULL`). No information is lost;
some is gained. **Flagged under §38 as a deviation needing approval.**

### `commitment_status`

Every outcome in §30 must stay distinguishable, so the enum is:

`pending` · `accepted` · `declined` · `expired` · `cancelled` · `no_show` ·
`stale` · `completed`

`declined` and `stale` are additions to the original six-value list, required
by the full specification. `cancelled` and `no_show` carry
`responsible_party` to say *who*; without it, "buyer no-show" and "seller
no-show" would be the same row.

### `commitment_party`

`buyer` · `seller`

### Mapping §30 onto these columns

| Situation | `status` | `responsible_party` |
| --- | --- | --- |
| Seller declines before acceptance | `declined` | null |
| Seller never responds within 24h | `expired` | `seller` (drives the ignored counter) |
| Buyer cancels after acceptance | `cancelled` | `buyer` |
| Seller cancels after acceptance | `cancelled` | `seller` |
| Buyer checks in, seller does not within 1h | `no_show` | `seller` |
| Seller checks in, buyer does not within 1h | `no_show` | `buyer` |
| Neither checks in | `stale` | null |
| Both check in, QR #1 never happens | `stale` | null |
| Both check in, QR #1 succeeds | `completed` | null |

Note the second row: the request *expired*, and the seller *ignored* it. Those
are two different facts about one event, and §5 requires both be kept. The
status records what happened to the request; `responsible_party` plus the
event log records the seller behaviour. No automatic penalty is applied.

### Declining is not held against anyone

Either party may decline before acceptance — the seller refusing a request, or
the buyer withdrawing their own. **Neither is a recorded behaviour.** The
`declined` status exists so the request has an honest end state, but it feeds
no counter and no reputation input.

This is deliberate. Saying no promptly is the *good* outcome: it frees the
seller's calendar and tells the buyer immediately. Penalising it would push
people to ignore requests instead, which is the behaviour the ignored counter
exists to discourage. Declining and ignoring must never both be recorded for
one request — they are opposites.

### A request that outlives its meetup

A `pending` request whose `scheduled_at` passes without ever being accepted
resolves to **`stale`**, not `expired`.

Under the lead-time rule above this should be unreachable: the request would
have expired five hours before the meetup. It is defined anyway because an
undefined state in a money-handling system is worse than a redundant rule — if
a clock skews or a scheduled job misses a run, the row still resolves somewhere
sensible. `stale` is the right destination: nobody acted, nobody is at fault,
and no stake was ever locked because acceptance never happened.

### When a request expires

A request has a 24-hour acceptance window, **but never one that runs so close
to the meetup that acceptance becomes useless.**

```
request_expires_at = LEAST(
    created_at   + market_settings.request_expiry_hours,        -- 24h
    scheduled_at - market_settings.minimum_acceptance_lead_hours -- 5h
)
```

Worked through: a buyer requests 5pm at 11am. The 24-hour window would run to
11am tomorrow, long past the meetup. The five-hour lead rule caps it at
**12pm** — if the seller has not accepted by noon, the request expires and the
seller gets an ignored event.

**Why the lead time exists.** An acceptance at 4:50pm for a 5pm meetup is worth
nothing to the buyer: they have not left the house, they may be at work, and
they cannot get there. Worse, the moment the seller accepts, the buyer's stake
is locked and the clock starts — so a late acceptance can push an honest buyer
straight into a no-show they had no way to avoid. The lead time makes sure that
by the time anyone's money is committed, both parties have real time to plan.

It also sets a floor on how soon a meetup can be requested at all: a request
for a time **less than five hours away is invalid**, because its deadline would
already have passed. This is enforced when the request is created, not later.

Both figures live in `market_settings` rather than in code, so they can be
tuned without a deployment.

Applying the deadline — flipping a request to `expired` once the moment passes
— belongs to a scheduled function, not to a page load. A request must expire
whether or not anybody happens to be looking at it.

### What a commitment is unique on

Two rules, both enforced in the database rather than in application code,
because both protect a promise made to a user.

**One live commitment per listing.** A listing is one physical item, so it
cannot be promised to two people at once. This is what `reserved` expresses.

**One accepted commitment per seller per moment.** A seller cannot be in two
places at once, even across different listings. Two accepted commitments at the
same instant would guarantee at least one no-show — and the model would then
penalise someone for a situation the platform created.

**One accepted commitment per buyer per moment**, for exactly the same reason.
The rule is symmetric: neither side can be in two places at once.

Taken together, a commitment is unique on **seller, item, and moment**, and
separately on **buyer and moment**.

Both are partial unique indexes restricted to live statuses, so a cancelled,
expired or stale commitment releases its hold and the listing returns to
`active`.

## 11. `commitment_events`

Append-only. Never updated, never deleted.

§31 requires that Kommitly can later answer: what happened, who did it, were
they acting as buyer or seller, when, and what outcome resulted. A status
column alone cannot — it only remembers the final state, and reputation is
built from the path, not the destination.

This table is also what lets the five aggregate counters on `profiles` stay
exactly as specified while still satisfying §8's requirement that buyer and
seller behaviour be distinguishable.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK. |
| `commitment_id` | `uuid` | no | FK to `commitments(id)`. |
| `event_type` | `commitment_event_type` | no | See below. |
| `actor_profile_id` | `uuid` | yes | Null for system-generated events such as expiry, where no user acted. |
| `actor_role` | `commitment_party` | yes | The role the actor held **in this commitment**. The same person is a buyer in one and a seller in another. |
| `occurred_at` | `timestamptz` | no | |
| `metadata` | `jsonb` | yes | Event-specific detail. Must never contain money amounts that belong in the ledger. |

### `commitment_event_type`

`request_created` · `seller_accepted` · `seller_declined` ·
`request_expired` · `buyer_cancelled` · `seller_cancelled` ·
`buyer_checked_in` · `seller_checked_in` · `buyer_no_show` ·
`seller_no_show` · `meetup_verified` · `commitment_stale` ·
`commitment_completed` · `purchase_completed`

Taken from §31, which offers them as an example rather than a mandate. Worth
confirming the list is right before it is built.

## 13. `meetup_verifications` — QR #1

| Field | Type | Null | Notes |

| `issued_at` | `timestamptz` | no | |

### Single use

**The code works exactly once.** On the first successful scan it is consumed,
the meetup is verified, and the code is dead — a second scan of the same code
fails, whoever presents it.

This is also what makes the token meaningful rather than decorative. A QR
encoding only the commitment id would be a static value: screenshot it, send it
to someone a hundred miles away, and they could "verify" a meetup that never
happened. A generated single-use token cannot be replayed, because the first
use destroys it.

The code is dead once the commitment completes regardless, so an unscanned code
on a finished commitment is never valid.

## 15. `wallets`

One per user **and one per charity**. Created by the wallet Cloud Function,
never by the app.

A charity receives forfeited stakes into a wallet exactly like any other
holder, so there is no separate payout path to build, test and reconcile. A
forfeit is an ordinary transfer between two wallets.

**A wallet and its address exist before any deposit.** One is created when the
account is created, not lazily on first deposit — a user needs an address to
send SOL to, so the address has to come first.

**Deposits are SOL only.** There is no bank or card funding path: a user tops
up by sending SOL to their wallet address, and it is credited as CAD at the
rate when it lands. Withdrawals go back out the same way.

**Exactly one of `profile_id` and `charity_id` is set**, enforced by a check
constraint. Two nullable foreign keys with a check are used rather than a
polymorphic `owner_type` / `owner_id` pair, because this keeps real referential
integrity — the database can still guarantee the owner exists, which a
polymorphic column cannot.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK. |
| `profile_id` | `uuid` | yes | FK to `profiles(id)`, unique. Set for a user's wallet. |
| `charity_id` | `uuid` | yes | FK to `charities(id)`, unique. Set for a charity's wallet. |
| `solana_address` | `text` | no | Public address, unique. **Public key only.** |
| `available_balance_cents` | `bigint` | no | Default 0. Spendable. |
| `locked_balance_cents` | `bigint` | no | Default 0. Held against active commitments. |
| `created_at` | `timestamptz` | no | |
| `updated_at` | `timestamptz` | no | |

**No private key, seed phrase or keypair is stored in this table or any other.**
The Cloud Function holds signing material in its own key management. If a
private key ever appears in a database column, that is a defect, not a design.

Both balances are non-negative, and together they must always equal the sum of
that wallet's completed ledger rows. Only the Cloud Function may write them,
and only in the same transaction as the ledger row that justifies the change —
otherwise a balance and its history can silently disagree, which is the one
failure mode that is genuinely painful to recover from.

`solana_address` is also **private between users.** §2 forbids exposing it from
one marketplace user to another, so it must never be returned by any query that
serves another user's page.

### `wallet_transaction_type`

`deposit` · `withdrawal` · `commitment_lock` · `commitment_refund` ·
`commitment_forfeit` · `purchase` · `sale`

Exactly the seven from the original model.

Three groupings behave differently and it is worth being explicit:

- `commitment_lock` and `commitment_refund` move money between the two balances
  **on a single wallet**. One row, no counterparty, no blockchain.
- `commitment_forfeit`, `purchase` and `sale` move money **between two
  wallets**, so each produces a pair of rows written together. A forfeit debits
  the user and credits the charity's wallet.
- `deposit` and `withdrawal` are the only types that cross the Solana boundary.

## 17. `market_settings`

**The general market configuration table.** A single row holding every value
that governs how the marketplace behaves, so those values can be changed while
the system is running rather than requiring a deployment.

Admin access only — see the access note at the end of this section.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `smallint` | no | PK, constrained to the value 1 so a second row cannot exist. |
| `currency_code` | `text` | no | `CAD`. Held here rather than assumed in code. |
| `base_commitment_fee_cents` | `bigint` | no | The market baseline stake, before individual reputation adjusts it. |
| `min_commitment_fee_cents` | `bigint` | no | Floor for any calculated stake. |
| `max_commitment_fee_cents` | `bigint` | no | Ceiling for any calculated stake. |
| `check_in_radius_metres` | `integer` | no | **200.** |
| `request_expiry_hours` | `integer` | no | **24.** Maximum acceptance window. |
| `minimum_acceptance_lead_hours` | `integer` | no | **5.** Minimum gap between acceptance and the meetup. Also the floor on how soon a meetup can be requested. |
| `check_in_window_minutes` | `integer` | no | **60.** |
| `vote_timezone` | `text` | no | `America/Vancouver`. Decides which calendar month a charity vote belongs to. |
| `active_charity_id` | `uuid` | yes | FK to `charities(id)`. Where forfeited stakes currently go. |
| `market_reputation` | `numeric` | yes | Written only by the reputation Cloud Function. Null until first calculated. |
| `market_reputation_params` | `jsonb` | no | Tuning inputs for the market reputation calculation. Default `{}`. |
| `user_reputation_params` | `jsonb` | no | Tuning inputs for individual reputation. Default `{}`. |
| `commitment_fee_params` | `jsonb` | no | Tuning inputs mapping reputation to a required stake. Default `{}`. |
| `updated_at` | `timestamptz` | no | |
| `updated_by` | `uuid` | yes | FK to `profiles(id)`. Who last changed configuration. |

### Why the floor and ceiling exist

`min_commitment_fee_cents` and `max_commitment_fee_cents` are not decoration.
The required stake is produced by a formula whose parameters can be edited at
runtime, which means a mistyped parameter could ask a user for a stake of one
cent or of ten thousand dollars. The bounds make a configuration error produce
a wrong-but-survivable number instead of a disaster, and they are enforced
wherever a stake is calculated — not merely suggested.

### Parameters, not formulas

These columns hold **numeric inputs to a fixed algorithm**, not the algorithm
itself. The reputation Cloud Function owns the shape of the calculation; this
table owns its tuning.

The distinction is deliberate, and it is a security one. A column holding an
expression that the service later evaluates is remote code execution with
extra steps: anyone who can write that row can run arbitrary code inside the
service that holds the custodial keys. Weights in JSONB give the same
day-to-day flexibility — "no-shows should count double this month" — with none
of that exposure.

If the *shape* of a formula genuinely needs to change, that is a change to the
function or to a versioned Postgres function, deployed and reviewed like any
other change. It should not be a text field.

**No formula is defined here.** Per §38, both reputation calculations and the
stake calculation belong to their Cloud Function, and this model only preserves
the inputs and the tuning.

### Access

Writable by administrators only. Every other role gets read access to the
operational values it needs — radius, expiry windows, base fee — and nothing
else. The parameter columns should not be readable by ordinary users: exposing
the exact weights behind reputation invites gaming them.

## 18. `market_settings_history`

Append-only. One row per change to `market_settings`.

`market_settings` holds a single mutable row, so editing it destroys what came
before. That matters because stakes and reputation scores are calculated from
those parameters: without a history, a stake charged last month cannot be
explained, and "why was I asked for $13?" has no answer once the weights have
moved on.

| Field | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | PK. |
| `changed_at` | `timestamptz` | no | |
| `changed_by` | `uuid` | yes | FK to `profiles(id)`. Null for a system or migration change. |
| `snapshot` | `jsonb` | no | The complete settings row **as it was after the change**. |
| `note` | `text` | yes | Optional reason for the change. |

A whole-row snapshot is stored rather than a field-level diff. A diff is
smaller but has to be replayed from the beginning to reconstruct any past
state, and a single missed row silently corrupts everything after it. A
snapshot answers "what were the parameters at 3pm on the 14th?" with one query
and no reconstruction.

Written by a database trigger on `market_settings`, not by application code, so
no path can update settings without recording the change.
